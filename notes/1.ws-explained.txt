First Question: What is a WebSocket?

Most tutorials say:

"WebSocket provides full-duplex communication."

That's technically correct but not very helpful.

A better explanation:

A WebSocket is a long-lived network connection between a client and a server.

Think:

Client -------------------- Server

Normally with HTTP:

Client ---- Request ----> Server

Client <--- Response ---- Server

Connection closed

After the response, the conversation is over.

With WebSockets:

Client -------- Connected -------- Server

The connection stays open.

Now:

Client ---> Server

or

Client <--- Server

at any time.

What Actually Happens Underneath?

A WebSocket is not a completely separate thing from HTTP.

This is where many people get confused.

The connection starts as HTTP.

Browser
   |
HTTP Request
   |
Server

The browser sends a special request:

GET /ws HTTP/1.1

Upgrade: websocket
Connection: Upgrade

The browser is basically saying:

"I don't want normal HTTP anymore. Let's switch to WebSocket."

Server responds:

101 Switching Protocols

Meaning:

"Okay, we're no longer speaking HTTP."

Now the connection becomes:

WebSocket Connection
So Do I Need an HTTP Server?

Usually:

YES

In most applications:

HTTP Server
     |
     +---- REST APIs
     |
     +---- WebSocket Upgrade Endpoint

Example:

GET /users
POST /login
PUT /profile

GET /ws

The /ws endpoint upgrades to a WebSocket connection.

Is WebSocket a Server?

This is a very good question.

Answer:

Kind of, but not exactly.

Let's use Node as an example.

You have:

This creates an HTTP server.

Then:

People see this and think:

HTTP Server
WebSocket Server

two completely separate things.

Not really.

More accurately:

HTTP Server
      |
      +---- Handles HTTP requests
      |
      +---- Handles WebSocket upgrades

The WebSocket server is sitting on top of the HTTP server.

Think:

Building
│
├── Reception Desk
│
└── Meeting Rooms

HTTP server:

Reception Desk

WebSocket server:

Meeting Rooms

Same building.

Different purpose.

The real answer (response to my answer)
---------------------------------------

Your answer is basically correct, but "connection details" is a bit too vague. Let's dig into what is actually happening.

Imagine this:

Browser A  <=======>  Server
Browser B  <=======>  Server

When Browser A connects, the server creates an object in memory.

In Node.js (ws library), it looks something like:

socketA

When Browser B connects:

socketB

Now the server has:

[
   socketA,
   socketB
]

or internally:

wss.clients

contains:

socketA
socketB
What exactly is a socket?

This is where most beginners get confused.

A socket is not just an IP address.

A socket is an object that represents the live communication channel between the browser and the server.

Think of it like this:

Person A ---- Telephone Line ---- Person B

The server stores the telephone line, not just the phone number.

Similarly:

Browser A ---- WebSocket Connection ---- Server

The server stores an object representing that open connection.

What information is inside that socket object?

The actual implementation differs by library, but conceptually it contains:

{
    ipAddress: "192.168.1.10",
    port: 52341,
    connectionState: "OPEN",

    send: function(){...},
    close: function(){...},

    internalBuffers: {...}
}

You can think of it as:

class Connection {
    ipAddress
    port

    send()
    receive()

    close()
}

The real object is much more complex, but that's the basic idea.

Why does the server need to store it?

Suppose Browser A sends:

"Hello everyone"

The server receives it.

Now it wants to send that message to everyone else.

How can it do that?

Because it has stored:

socketA
socketB

So it can do:

socketA.send("Hello everyone")
socketB.send("Hello everyone")

Without storing those socket objects, the server wouldn't know where to send messages.

What if the server only stored IP addresses?

Imagine:

[
   "192.168.1.10",
   "192.168.1.11"
]

Could the server do:

"192.168.1.10".send("Hello")

No.

An IP address only tells you where a machine is.

It doesn't represent the active communication channel.

The socket object represents the actual live connection.

A real chat application

Suppose three users join.

John
Mary
Alex

The server might keep:

const clients = new Map();

clients.set(socketA, {
    userId: 1,
    username: "John"
});

clients.set(socketB, {
    userId: 2,
    username: "Mary"
});

clients.set(socketC, {
    userId: 3,
    username: "Alex"
});

Notice something important:

The server is not storing just user data.

It is storing:

Connection Object (socket)
        +
User Information

because when Mary receives a message, the server needs her socket to send it.

How does this relate to Go?

When you saw:

Clients map[*websocket.Conn]bool

the hub was storing:

Connection A -> true
Connection B -> true
Connection C -> true

where each:

*websocket.Conn

is equivalent to Node's:

socket

Both represent:

A live WebSocket connection

between one client and the server.

The most accurate version of your answer

Instead of saying:

"The server stores the connection details."

I would say:

"The server stores a connection object (socket or websocket connection) for each connected client. That object represents the live communication channel and contains everything needed to send messages to that client and manage the connection."

That is very close to how real WebSocket servers work internally.
